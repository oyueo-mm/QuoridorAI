# 2단계 보고서 — Alpha-Beta 강화 (1차: 벽 후보 필터, 비트보드 BFS)

브랜치 `stage1-benchmark` · 1단계 보고서: [stage1-performance-report.md](stage1-performance-report.md)

표기: **[실측]** 이번에 측정한 값, **[확인]** 테스트·코드로 확인한 사실, **[추정]**, **[미검증]**.

## 요약

- **비트보드 BFS 채택**: 결과가 기존 구현과 완전히 같고(노드 단위 동일), Alpha-Beta 탐색이 1.5× 빨라짐. 동일 시간 200판에서 승률 차이는 관찰되지 않음(48.1%, CI 41–55).
- **벽 필터 문제 원인 규명·해결 옵션 구현**: 놓친 승리는 상대의 경로 차단 자리를 미리 막는 "보호 벽" 때문. `path-defense`는 그 승리를 찾지만, 항상 켜면 탐색이 1.1 ply 얕아져 **동일 시간 35.9%(−100 Elo)로 약해짐 → 기본값 불채택**.
- **진행 중**: 목표 3칸 이내에서만 보호 벽을 넣는 변형(S6), 비트보드 적용 후 기본 AB vs Guided MCTS(S7).

## 1. 변경 내용

### 1.1 벽 후보 필터 `path-defense` (`src/ai/search/candidates.ts`)

1단계 전술 테스트에서 AB는 깊이 5·300 ms·2 s 모두 같은 5 ply 강제 승리(F4/g178/p55)를 놓쳤습니다. 진단 결과 [확인]:

- AB 쪽(P1)은 목표까지 2칸, 상대는 8칸이지만 벽 2개 보유. 이기는 수 `f1h e1v f1v`는 **어느 쪽 경로도 끊지 않는 벽**.
- 그중 `f1h`, `e1v`는 상대가 P1의 최단 경로를 끊는 데 쓸 자리(`e1h`)를 겹침·교차로 **미리 막는 보호 벽**. 기존 필터(`opponent-path`: 상대 최단 경로를 끊는 벽만)는 이런 수를 영원히 보지 못함(합법 벽 75개 중 7개만 탐색).

`path-defense` = `opponent-path` 후보 + **상대에게 벽이 남아 있을 때**, 내 현재 최단 경로를 끊을 수 있는 각 자리에 대해 그 자리를 겹치거나 교차해 무력화하는 벽(그 자리 자체는 제외 — 자기 경로를 끊음).
합법성 검사는 기존 지연 방식 그대로(경로를 끊는 벽만 BFS). 설정 `wallFilter: 'path-defense'`.

### 1.2 행 마스크 비트보드 BFS (`src/engine/rowMasks.ts`)

1단계 프로파일에서 탐색 CPU의 약 70%가 칸 단위 BFS(`canStep → isBlocked → hasHWall` 호출 사슬)였습니다.

- 벽 배치마다 행별 9비트 정수 4종(동·서·남·북으로 이동 가능한 열)을 한 번 계산해 캐시(불변 `Uint8Array` 쌍을 키로 하는 `WeakMap`).
- `distanceToRow`: 프런티어 한 행을 시프트·AND 몇 번으로 확장하는 층 단위 BFS. `hasPathToRow`: 행 안 수평 폐포를 한 번에 채우는 flood fill. `distanceMap`: 다중 소스 층 BFS.
- `shortestPath`: 탐색 후보가 **어떤 최단 경로가 반환되는지**에 좌우되므로, 기존과 같은 큐 순서·이웃 순서(상하좌우)를 유지하고 간선 검사만 마스크 조회로 바꿔 **같은 경로**를 반환.
- 엔진 공개 함수(`distanceToRow`, `hasPathToRow`, `distanceMap`, `shortestPath`)는 커널 스위치로 두 구현 중 하나를 호출(기본 `masked`). 기존 구현은 `*Reference`로 보존.
  탐색마다 `MinimaxSettings.pathKernel`로 고를 수 있어 **같은 프로세스에서 신·구 AB 대국**이 가능(결정은 동기 실행이라 안전).
- 3·4인전(`shortestPathToGoal` 등 열 목표)과 변형 모드의 자체 BFS는 변경하지 않음. 행 목표를 쓰는 다인전 호출은 동치 테스트로 결과 동일 확인.

### 1.3 실험 지원

- `AgentSpec.minimax`(설정 덮어쓰기)·`tag`(라벨) — 배치 실험 전용, 브라우저는 사용하지 않음. 기존 설정 해시 불변.
- 스위트 `stage2`(S1–S5, 결과 `bench/results/stage2/`), 구성 요소 벤치 `bench/stage2.bench.test.ts`, 전술 에이전트 `ab4-pd`·`ab5-pd`·`ab-300ms-pd`·`ab-2s-pd`.

## 3. 성능 측정

### 3.3 동일 시간 대국 (300 ms/수, mixed 고유 오프닝, 선후공 교환)

**측정 조건 주의 [확인]:** 20:10–23:55 사이 노트북이 여러 번 절전에 들어가 한 수가 69분·96분 걸린 기록이 있습니다. 같은 프로세스·같은 대국 안의 두 에이전트는 같은 조건을 겪지만,
절전을 가로지른 수는 공정하지 않으므로 **예산 3배를 넘은 수가 있는 대국의 쌍 전체를 제외**한 값을 주 결과로 씁니다(`bench/lib/analyze-clean.py`, 포함한 값도 병기).
이 시간대 nodes/s(약 20–30k)가 유휴 측정(50–63k)보다 낮아 절전 전후 CPU 클럭 저하도 있었던 것으로 보입니다 [추정] — 같은 대국 안 두 쪽에 같이 적용됩니다.

|---|---|---|---|---|---|---|---:|

| **S2** `path-defense` vs `opponent-path` (BFS 동일) | 진행 중* | **35.9% (28.1–44.5)** | **−100 (−163 … −38)** | 0.365 (0.298–0.432) | 5.83 / 6.91 | 32.6 / 29.0 | 5 |

- **S1 [실측]**: 같은 대국에서 비트보드 쪽이 노드를 24% 더 빨리 탐색했지만(깊이 +0.19) **승률 차이는 관찰되지 않음**. 깊이 +0.2 ply의 기대 효과(약 +10–20 Elo [추정])는 200판으로 검출할 수 없는 크기입니다.
- **S2 [실측]**: 항상 켜진 보호 벽은 탐색 깊이를 약 1.1 ply 줄여 **유의하게 약해짐**. 전술 이득(국면 1개)보다 깊이 손실이 큽니다.

## 4. 채택 결정

| 변경 | 결정 | 근거 |
|---|---|---|
| 비트보드 BFS (엔진 기본값 `masked`) | **채택** | 결과가 기존과 완전히 같음(규칙·탐색 노드 동일)이 증명되고, 속도 향상이 실측됨(탐색 1.5×, 벽 합법성 7–8×). 실력 향상은 **관찰되지 않음** — 순수 최적화로만 채택 |
| `path-defense`(항상) | **기본값 불채택** (옵션으로 유지) | S2: 동일 시간 35.9%, −100 Elo |
| `path-defense` + `defenseMaxDistance: 3` | **판정 대기** | S6(동일 시간)·pd3 전술 결과 필요. 이기면 기본값 후보, 아니면 옵션으로만 유지 |

현재 기본 Alpha-Beta 설정(`DEFAULT_MINIMAX_SETTINGS`)은 바뀌지 않았습니다(`opponent-path`). 웹 UI 코드 변경 없음.

## 5. 다음 단계 제안 [추정]

1. 측정상 탐색 시간의 남은 큰 몫은 **후보 생성·정렬용 평가**(1단계 `expand` 46%)와 리프 평가입니다. 비트보드로 BFS가 줄었으니 다음 병목을 다시 프로파일링한 뒤(`bench/profile.bench.test.ts`) 정렬 평가 축소, 배열 TT, PVS를 적용합니다.
2. 보호 벽은 "가치 있는 소수"만 넣어야 합니다 — 정렬 맨 뒤 + 늦은 수 감축(LMR), 또는 상대 벽이 남았을 때 경주가 접전인 노드에만 허용.
3. 1단계에서 확인한 대로 동일 시간 Elo 차이를 검출하려면 400판 이상이 필요한 경우가 많습니다 — 2단계 이후 비교는 SPRT(순차 검정)로 판 수를 자동 결정하는 것이 효율적입니다.
4. 장시간 측정은 절전 방지 상태에서 실행합니다(`bench/keep-awake.ps1`, 덮개 닫힘은 막지 못함).
